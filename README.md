# my-service-agent — OO제약사 사규 안내 챗봇

## 서비스 소개

OO제약사 2021 통합규정집(47개 규정, 1,158개 조문, 462페이지)을 근거로 임직원의 사규 질문에 답하는 사내 안내 챗봇이다. 하이브리드 검색(코사인 유사도 + BM25)으로 관련 조항을 찾고, 로컬 LLM(Ollama, qwen3.5:2b)이 그 조항만 근거로 답을 생성·스트리밍한다. 모든 답변에는 출처(규정명·조·페이지) 칩이 붙고, 답변 직후 자동 판정(LLM-as-a-judge)이 근거 충실도를 다시 한번 확인한다. 실제 동작하는 구현체는 별도 저장소 `dongkook-rag-chatbot/`(`server/`, `static/`, `scripts/`)에 있고, 이 저장소(`my-service-agent/`)는 그 서비스를 설계 관점에서 다시 정리한 패킷이다.

## 설계 결정 요약

**도구를 4개만 둔 이유.** 이 챗봇은 사규 원문을 찾아 보여주는 것이 전부이고, 예약을 확정하거나 규정을 수정하거나 개인정보를 열람하는 기능은 애초에 없다. 그래서 도구도 "찾는다(search_regulation)", "정확히 지목된 걸 그대로 가져온다(get_regulation_article)", "답할 수 없으면 이관한다(escalate_to_department)", "사람이 누른 평가를 기록한다(log_feedback)" 4개로 충분했다. 더 쪼개거나 늘리면 모델이 어떤 도구를 쓸지 헷갈리는 경계 문제만 늘어난다고 판단했다.

**권한을 읽기/쓰기로 나눈 기준.** 상태를 바꾸는지 여부로 나눴다. `search_regulation`과 `get_regulation_article`은 벡터스토어를 읽기만 하므로 승인이 필요 없다. `escalate_to_department`도 안내 문구를 만들 뿐 아무 상태도 바꾸지 않는다. 유일한 쓰기 도구인 `log_feedback`은 사람(사용자 본인)이 버튼을 직접 눌렀을 때만 호출되고, 되돌릴 필요가 없는 append-only 로그라서 별도 승인 절차 없이도 안전하다고 판단했다.

**실패 뒤 행동을 그렇게 정한 근거.** 실제로 구현하고 브라우저에서 테스트하면서 두 가지를 직접 겪었다: (1) 로컬 LLM(qwen3.5:2b)의 "생각(thinking)" 모드가 기본으로 켜져 있어 응답이 사실상 멈춘 것처럼 보이는 문제 — `think:false`로 해결했고, 이후 "연결 실패 시 1회만 재시도 후 중단"이라는 규칙의 필요성을 체감했다. (2) 검색 결과가 같은 조(제27조)의 하위 조각으로만 채워져 정작 필요한 항이 빠지는 문제 — "score 낮으면 재시도 없이 근거 없음으로 전환"이라는 규칙만으로는 부족하고, 애초에 도구가 반환하는 근거 자체가 완전해야 함을 확인해 조 단위로 원문을 병합하도록 고쳤다(자세한 내용은 [my-agent/traces/trace-01.txt](my-agent/traces/trace-01.txt)).

## 실행하지 않은 것과 이유

- **regulation_filter 오타 교정(유사 규정명 제안)**: 사용자가 "출장규정"처럼 축약된 이름을 쓰면 현재는 47개 후보 목록을 통째로 보여주고 되묻기만 한다. 문자열 유사도로 1~2개를 먼저 제안하는 기능은 구현하지 않았다 — 지금은 정확도보다 "잘못된 규정명을 모델이 지어내지 않는다"는 안전장치를 먼저 검증하는 게 우선순위였다. 다음에 측정할 지점: 되묻기 왕복 횟수가 실제로 사용성에 얼마나 영향을 주는지.
- **답변 첫 문장에 핵심 수치 명시 규칙의 재검증**: 시스템 지시에 규칙은 추가했지만(`server/app.py`), 로컬 모델의 응답 속도(질문 하나에 수십 초~수 분) 때문에 수정 후 실제 답변으로 재검증하지 못했다. 다음에 측정할 지점: 이 규칙이 실제로 qwen3.5:2b의 답변 품질을 개선하는지, 아니면 더 큰 모델이나 API로 바꿔야 하는지.
- **get_regulation_article의 실제 API 엔드포인트 분리**: 현재 구현(`server/app.py`)은 출처 칩 클릭 시 프런트엔드가 이미 받아온 검색 결과에서 원문을 보여주는 방식이라, `get_regulation_article`을 별도 HTTP 엔드포인트로 분리하지는 않았다. 설계 문서상으로는 독립된 도구 계약으로 정의해 두었고(정확한 조 지목 시의 결정론적 조회라는 책임이 `search_regulation`과 다르기 때문), 실제 분리 구현은 다음 단계로 미뤘다.
- **다중 턴 대화 컨텍스트 유지**: 현재는 매 질문을 독립적으로 처리한다. "그럼 반차는요?" 같은 후속 질문에서 이전 문맥(연차휴가)을 이어받는 기능은 구현하지 않았다 — 근거 추적이 한 턴 안에서 끝나야 출처 표기가 애매해지지 않는다고 판단해 범위에서 제외했다.

## 폴더 구조

```
my-service-agent/
├── README.md
├── design-packet.md
└── my-agent/
    ├── tool-definition.md
    └── traces/
        ├── trace-01.txt   # 정상 경로: 연차휴가 질문
        ├── trace-02.txt   # 취소: 스트리밍 중 사용자 취소
        ├── trace-03.txt   # 경계: 존재하지 않는 regulation_filter
        └── trace-04.txt   # 경계: 빈 질문
```

실제 서비스 구현은 별도 저장소 `dongkook-rag-chatbot/`(`server/`, `static/`, `scripts/`, `data/`, `PRD.md`)에 있다. 이 폴더(`my-service-agent-dongkook/`)는 그 구현체를 설계 관점에서 별도 문서로 정리한 제출용 패킷이다.
